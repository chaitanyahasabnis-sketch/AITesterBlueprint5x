1. Overview

This plan covers the VWO login experience at app.vwo.com, from initial page load through authentication, recovery, and transition to the authenticated dashboard. It is based on the supplied PRD, which describes email/password authentication, session management, optional multi-factor authentication (MFA), enterprise single sign-on (SSO), password recovery, accessibility, mobile behavior, security, performance, integrations, and success measures.

ProductVWO Login Dashboard
Primary objectiveEnable secure, low-friction access while protecting accounts and meeting enterprise, usability, and compliance expectations.
Primary usersDigital marketers, product managers, UX designers, developers, enterprise teams, CRO specialists, and analysts.
Release approachPhase 1 core authentication; Phase 2 enhanced UX and accessibility; Phase 3 enterprise features and analytics.
Plan ownerQA/Test Lead (to be assigned)
Scope caveat: The PRD is a broad product vision and does not specify several implementation policies (for example, password rules, lockout thresholds, session duration, exact browser support, or SSO provider configuration). These are recorded as assumptions and must be confirmed before final test-case sign-off; tests must not invent product behavior.

Success measures from the PRD

  • Authentication success rate target: 95% or higher for eligible attempts.
  • Login page load target: under 2 seconds on standard connections.
  • User satisfaction target: 90% or higher.
  • Zero successful brute-force attacks or unauthorized access incidents.
  • 100% adherence to applicable security audit requirements; reduce login-related support tickets by 20%.

2. Scope

In scope

  • Login page rendering, branding, responsive layout, light/dark theme, auto-focus, clickable labels, and loading feedback.
  • Email/password validation, authentication success/failure, actionable errors, remember-me behavior, session creation/timeout, and logout/session invalidation where supported.
  • Password reset request, secure reset token lifecycle, recovery email, password policy, and post-reset login.
  • Optional MFA enrollment/challenge/recovery and enterprise SSO paths (SAML/OAuth or the configured protocols), when enabled for the release.
  • Rate limiting and account/session protection; secure transport, storage, token handling, and privacy/compliance checks.
  • Transition to the VWO dashboard, preservation of appropriate navigation context, login analytics, and login assistance/support integration.
  • Keyboard and screen reader accessibility, high contrast, WCAG 2.1 AA evaluation, cross-browser/device behavior, and performance/load/availability checks.

Out of scope for this release unless explicitly enabled

  • Biometric and adaptive authentication, progressive web app behavior, personalized login content, and future A/B optimization features.
  • Functional validation of the full VWO dashboard after login beyond verifying successful, authorized handoff and basic landing-page availability.
  • Third-party identity-provider internals, marketing platform internals, or production penetration testing; integration contracts and safe test-environment behavior remain in scope.

3. Test Strategy

  1. Risk first: Prioritize credential handling, unauthorized access, recovery-token abuse, session security, brute-force protections, and SSO/MFA before visual polish.
  2. Traceability: Map every planned scenario to one or more requirement IDs in section 10. Link execution records and defects to the same IDs.
  3. Layered validation: Validate business rules at unit/service level, authentication and integrations at API/contract level, then critical user journeys in browser E2E.
  4. Positive and negative coverage: Include valid, invalid, boundary, expired, replayed, interrupted, and unavailable-service cases. At least 40% of detailed scenarios should exercise negative/error behavior.
  5. Privacy-safe testing: Use synthetic accounts and data, redact credentials/tokens from logs, and verify that analytics and error responses do not expose secrets or personal data.
  6. Shift left and repeat: Review requirements and security design early; run smoke checks per build, focused regression on changes, and full release regression before go-live.
  7. Release phasing: Gate Phase 1 on core authentication/recovery; Phase 2 on responsive/accessibility; Phase 3 on SSO/MFA/enterprise controls and analytics where those features are part of the release.

Test design techniques

  • Equivalence classes for email, password, account status, identity-provider responses, and recovery-token states.
  • Boundary analysis for configured password limits, session expiry, token lifetime, rate-limit thresholds, viewport breakpoints, and performance targets.
  • Decision tables for valid/invalid credentials × account state × MFA/SSO policy × rate-limit state.
  • State-transition testing for login, MFA challenge, password reset, session renewal/expiry, logout, and retry/lockout workflows.
  • Exploratory testing for usability, browser/device differences, localization readiness, and error recovery.

5. Entry and Exit Criteria

Entry criteria

  • PRD and acceptance criteria reviewed; open questions affecting test outcomes are resolved or explicitly accepted as release assumptions.
  • Build deployed to a stable, isolated test environment; smoke test passes and test endpoints are identifiable.
  • Authentication, password, session, rate-limit, MFA, and SSO policies/configurations are documented for the target release.
  • Test accounts, synthetic data, mail capture, identity-provider sandbox, and monitoring/log access are available.
  • Supported browser/device matrix, performance workload, data-retention rules, and security-test authorization are agreed.
  • Test cases are reviewed and traceable; defect triage severity/priority rules and release contacts are defined.

Exit criteria

  • 100% of P0 and P1 scenarios executed; at least 95% of all planned release scenarios executed, with remaining tests waived and risk-accepted.
  • All P0/P1 tests pass; all failures are resolved or formally accepted with owner, mitigation, and expiry date.
  • No open Critical/High security defects, unauthorized access paths, or unresolved compliance blockers.
  • Core login, reset, and applicable MFA/SSO regression passes on the agreed supported browser/device matrix.
  • Page-load target under 2 seconds is met under the agreed standard-connection measurement; agreed load and availability targets are met.
  • WCAG 2.1 AA assessment has no unresolved critical/blocking violations; remaining exceptions are documented and approved.
  • Authentication success rate, security monitoring, and analytics event correctness meet approved acceptance criteria; no secrets appear in client or server logs.
  • Test summary, requirement traceability, defect disposition, residual risks, and stakeholder sign-offs are published.

7. Test Data Requirements

  • Create synthetic accounts for active, unverified (if applicable), disabled, locked/throttled, MFA-enabled, SSO-managed, and password-expired states.
  • Use valid and invalid email classes: normal valid address, malformed syntax, empty, overlong, internationalized if supported, and duplicate/existing identity.
  • Cover password inputs at policy boundaries (below/at/above each configured rule), incorrect/correct credentials, leading/trailing whitespace, Unicode, and maximum accepted length. Exact policy comes from product/security configuration.
  • Prepare reset tokens that are valid, expired, already used, malformed, tampered, and invalidated after a subsequent reset; keep tokens out of screenshots and logs.
  • Prepare MFA cases for valid/invalid/expired/replayed challenge, recovery path, clock drift where relevant, and unavailable provider; use sandbox secrets only.
  • Prepare SSO scenarios for successful assertion, denied/cancelled login, invalid signature/state/nonce, expired assertion, unprovisioned user, and IdP outage, as applicable to configured protocols.
  • Generate load-test identities with non-personal synthetic attributes; ensure data is reset or expired after each run.
  • Use only authorized test accounts; never use real customer credentials or expose passwords, reset links, session cookies, or MFA secrets in reports.

Assumptions and open questions for approval

  1. What exact password complexity/length policy, history/reuse rules, and password-expiry behavior apply?
  2. What are the session idle/absolute timeouts, remember-me duration, cookie/token requirements, and logout/revocation semantics?
  3. What are the login/reset/MFA attempt thresholds, throttling response, lockout duration, and account recovery rules?
  4. Which MFA methods, enrollment rules, fallback/recovery mechanisms, and tenant policies are in this release?
  5. Which SSO providers/protocols and identity provisioning policies are supported; is social login in scope?
  6. Which browsers/versions, operating systems, mobile devices, regions, and locales are officially supported?
  7. For the under-2-second load metric, what percentile, network profile, geographic location, and measurement boundary define acceptance?
  8. What peak concurrent-user model, availability measurement window, recovery objective, and planned maintenance exclusions apply to the 99.9% target?
  9. Which analytics events, consent requirements, retention periods, and GDPR/CCPA/enterprise audit controls are mandatory?
  10. Are the theme options, signup path, analytics/support links, and recent-activity context included in the release under test?
Approval gate: Resolve or formally accept these questions before finalizing detailed expected results and release exit status. Any unimplemented optional feature should be marked not applicable with a product-approved rationale, not counted as a passing test.
