Defect Tracking

CRISPskill: defect-tracker

Produce a defect board update: status, aging, stale and reopened bugs, and owner actions.

Template file: 05_Defect_Tracking_CRISP.md

1. When to use it

Use when

  • Weekly or daily defect review
  • Before a release go/no-go

Skip when

  • You are deciding severity of new bugs (use 08 Bug Triaging)

2. How the CRISP framework is used here

C
Context — The background and raw input the model works from.
In this template: [PASTE DEFECT LIST]
R
Role — The expert persona the model writes as.
In this template: Act as a QA Lead maintaining the defect board.
I
Instructions — What to produce and the rules for producing it.
In this template: 1. Counts by status and by severity
S
Style — Tone, length and audience.
In this template: Scannable tables, neutral tone, no blame.
P
Parameters — Hard output constraints: counts, limits, labels for missing data.
In this template: - One page.

3. Gather your inputs first

  • Defect export: ID, title, severity, priority, status, assignee, created, updated, reopen count
  • Report date
  • Stale threshold in days

For project background, fill the blank pack in ../00_context-template/ and paste it above the prompt. ../00_context-vwo/ is a filled example.

4. Run it step by step

  1. Open 05_Defect_Tracking_CRISP.md and copy the whole Prompt block.
  2. Replace every [PLACEHOLDER] with your inputs. Leave a placeholder as Not supplied rather than guessing.
  3. Keep the GUARDRAILS block at the end. It stops the model inventing facts.
  4. Paste into Claude (or your agent) and ask for the output in the format you need (Markdown, DOCX, XLSX).
  5. Check the result against the review checklist in step 6.
  6. Save the output in ../output/ and add a row to ../MyNotes.md.

The prompt you will paste:

## C: Context
Defect export for [PROJECT / RELEASE] as of [REPORT DATE]:
[PASTE DEFECT LIST]

## R: Role
Act as a QA Lead maintaining the defect board.

## I: Instructions
Produce:
1. Counts by status and by severity
2. Aging: days open from 'created' to report date
3. Stale defects: no update for more than [N] days
4. Reopened defects
5. Release blockers: Critical/High still open
6. Actions per owner
Compute only from the data. Missing fields: 'Not supplied'.

## S: Style
Scannable tables, neutral tone, no blame.

## P: Parameters
- One page.
- Sort by severity, then age.
- Dates as YYYY-MM-DD.

GUARDRAILS (always apply)
- Use ONLY the information pasted into this prompt.
- Do NOT invent requirements, IDs, error messages, numbers, dates or behaviour.
- Missing information -> write "Requires clarification" or "Not supplied".
- Inferred information -> label it "Inference (low confidence)".
- Synthetic data and placeholders only (e.g. <registered_test_email>). No real credentials or personal data.
- Finish with a short Self-Check: list anything you could not trace to the input.

5. Worked example (VWO login)

Input (excerpt): BUG-101 | Login no validation | High | Open | dev-a | created 2026-11-12 | updated 2026-11-12; report date 2026-11-21; stale > 5 days

Good output looks like:

| BUG-101 | Login no validation | High | Open | dev-a | 9 | 2026-11-12 | Stale, Blocker |

Expected output format:

| Defect ID | Title | Severity | Status | Assignee | Age (days) | Last Update | Flag (Stale / Reopened / Blocker) |

6. Review before you trust it

  • Ages are computed from the given dates
  • Every blocker is High/Critical and open
  • No defects added or dropped
  • Actions name an owner

7. Common problems and fixes

ProblemFix
Ages computed from today's real dateState the report date explicitly in Context.
Statuses renamedAsk it to keep status values exactly as exported.
