Regression Testing

CLEARskill: regression-planner

Select a risk-based regression set from existing tests for a specific change, within a time budget.

Template file: 09_Regression_Testing_CLEAR.md

1. When to use it

Use when

  • A release or significant change is coming
  • You must cut regression to fit time

Skip when

  • Only a quick build check is needed (use 07)

2. How the CLEAR framework is used here

C
Context — The background and raw input the model works from.
In this template: Act as a QA Lead planning regression for [RELEASE].
L
Limits — Hard rules the output must not break (scope, IDs, invented facts).
In this template: 1. Select only supplied test IDs; suggestions for new tests go in a separate list.
E
Examples — The output format plus one filled row to copy.
In this template: Row: TC-001 | Valid login | Critical | Login module changed | Automated | 1
A
Action — The analysis steps and rules the model must follow.
In this template: Map changed areas to dependent areas, then place tests in tiers: Critical (must run), Impacted, Extended (if time allows). Give an execution order.
R
Review — The self-check the model runs before handing over.
In this template: 1. Every changed area has at least one test.

3. Gather your inputs first

  • Change description (tickets, modules, PR summary)
  • Existing test suite (IDs, titles, area, automated Y/N, duration)
  • Time budget

For project background, paste the files in ../00_context-vwo/ above the prompt.

4. Run it step by step

  1. Open 09_Regression_Testing_CLEAR.md and copy the whole Prompt block.
  2. Replace every [PLACEHOLDER] with your inputs. Leave a placeholder as Not supplied rather than guessing.
  3. Keep the GUARDRAILS block at the end. It stops the model inventing facts.
  4. Paste into Claude (or your agent) and ask for the output in the format you need (Markdown, DOCX, XLSX).
  5. Check the result against the review checklist in step 6.
  6. Save the output in ../output/ and add a row to ../MyNotes.md.

The prompt you will paste:

## C: Context
Act as a QA Lead planning regression for [RELEASE].
Changes:
[PASTE]
Existing tests:
[PASTE TC ID | Title | Area | Automated | Minutes]
Time budget: [HOURS]

## L: Limits
1. Select only supplied test IDs; suggestions for new tests go in a separate list.
2. Justify every selection by change impact.
3. Respect the time budget; automated tests count separately from manual time.

## E: Examples
Row: TC-001 | Valid login | Critical | Login module changed | Automated | 1

## A: Action
Map changed areas to dependent areas, then place tests in tiers: Critical (must run), Impacted, Extended (if time allows). Give an execution order.

## R: Review
1. Every changed area has at least one test.
2. Manual time total within budget.
3. Gaps -> new tests to write.
4. Risk statement if Extended is skipped.

GUARDRAILS (always apply)
- Use ONLY the information pasted into this prompt.
- Do NOT invent requirements, IDs, error messages, numbers, dates or behaviour.
- Missing information -> write "Requires clarification" or "Not supplied".
- Inferred information -> label it "Inference (low confidence)".
- Synthetic data and placeholders only (e.g. <registered_test_email>). No real credentials or personal data.
- Finish with a short Self-Check: list anything you could not trace to the input.

5. Worked example (VWO login)

Input (excerpt): Change: login validation fix (BUG-101). Budget 2 hours.

Good output looks like:

| TC-006 | Empty password | Critical | Directly changed | Yes | 1 |
Gap: no test for whitespace-only password -> write new test.

Expected output format:

| TC ID | Title | Tier | Reason (impact) | Automated | Minutes |

6. Review before you trust it

  • Only supplied IDs
  • Each selection has an impact reason
  • Time totals shown
  • Gaps listed separately

7. Common problems and fixes

ProblemFix
Whole suite selectedAsk it to cut to the time budget and show the total.
New test IDs mixed into the selectionRepeat Limit 1.
