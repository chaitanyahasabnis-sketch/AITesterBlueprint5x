Smoke and Sanity Testing

CLEARskill: smoke-sanity-planner

Produce a short, time-boxed smoke or sanity checklist with an explicit go/no-go rule.

Template file: 07_Smoke_Sanity_Testing_CLEAR.md

1. When to use it

Use when

  • A new build lands (smoke: broad and shallow)
  • A fix or small change lands (sanity: narrow and deep)

Skip when

  • You need full regression scope (use 09)

2. How the CLEAR framework is used here

C
Context — The background and raw input the model works from.
In this template: Build [BUILD] is deployed to [ENVIRONMENT]. Run type: [Smoke / Sanity].
L

E
Examples — The output format plus one filled row to copy.
In this template: Row: SM-01 | Login | Log in with valid test account | Dashboard opens | Pass if dashboard loads | 2
A
Action — The analysis steps and rules the model must follow.
In this template: Generate the checklist and a go/no-go rule. For sanity, include verification of the fix plus adjacent checks.
R
Review — The self-check the model runs before handing over.
In this template: 1. Each critical flow is covered once.

3. Gather your inputs first

  • Build number and environment
  • Smoke or Sanity
  • Critical flows list
  • Change / fix notes (for sanity)
  • Time box

For project background, paste the files in ../00_context-vwo/ above the prompt.

4. Run it step by step

  1. Open 07_Smoke_Sanity_Testing_CLEAR.md and copy the whole Prompt block.
  2. Replace every [PLACEHOLDER] with your inputs. Leave a placeholder as Not supplied rather than guessing.
  3. Keep the GUARDRAILS block at the end. It stops the model inventing facts.
  4. Paste into Claude (or your agent) and ask for the output in the format you need (Markdown, DOCX, XLSX).
  5. Check the result against the review checklist in step 6.
  6. Save the output in ../output/ and add a row to ../MyNotes.md.

The prompt you will paste:

## C: Context
Build [BUILD] is deployed to [ENVIRONMENT]. Run type: [Smoke / Sanity].
Critical flows:
[PASTE]
Change or fix notes (sanity):
[PASTE or Not supplied]

## L: Limits
1. Smoke: at most [15] checks, total time <= [30] minutes, one check per critical flow.
2. Sanity: only the changed area and directly connected flows.
3. Use only the supplied flows; do not invent features.
4. Every check has a clear pass/fail criterion.

## E: Examples
Row: SM-01 | Login | Log in with valid test account | Dashboard opens | Pass if dashboard loads | 2

## A: Action
Generate the checklist and a go/no-go rule. For sanity, include verification of the fix plus adjacent checks.

## R: Review
1. Each critical flow is covered once.
2. Total time fits the time box.
3. Go/no-go rule is explicit (e.g. any P0 check fails = no-go).
4. List data or accounts needed.

GUARDRAILS (always apply)
- Use ONLY the information pasted into this prompt.
- Do NOT invent requirements, IDs, error messages, numbers, dates or behaviour.
- Missing information -> write "Requires clarification" or "Not supplied".
- Inferred information -> label it "Inference (low confidence)".
- Synthetic data and placeholders only (e.g. <registered_test_email>). No real credentials or personal data.
- Finish with a short Self-Check: list anything you could not trace to the input.

5. Worked example (VWO login)

Input (excerpt): Sanity after fix for BUG-101 (empty password validation).

Good output looks like:

| SN-01 | Login | Submit with empty password | Login blocked, validation shown | Pass if not logged in and a message is visible | 2 |
Go/No-Go: SN-01 fails = reject build.

Expected output format:

| Check ID | Flow | Steps | Expected | Pass Criterion | Time (min) |  + Go / No-Go rule

6. Review before you trust it

  • Within the check and time limits
  • Go/no-go rule is stated
  • Sanity stays near the change
  • Only supplied flows used

7. Common problems and fixes

ProblemFix
Smoke list grows into regressionReduce the limit and ask for the most critical check per flow.
No go/no-go ruleAsk for the Review step output explicitly.
