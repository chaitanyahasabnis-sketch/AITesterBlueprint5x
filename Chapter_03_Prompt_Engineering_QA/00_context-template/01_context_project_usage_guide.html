Project Context

Describes the application as a whole, so every prompt knows what product, users and environments it is dealing with.

Blank file: 01_context_project.md · Filled example: 00_context-vwo/01_context_project.md

1. Why this file matters

The model uses the domain and users to choose relevant risks, and the environments and URLs to fill test plans and bug reports instead of inventing them.

When to fill it

Once per project. Update it when environments, tech stack or objectives change.

Golden rule

Only write what a source document says. Anything else is [Requires clarification].

2. Where to find the information

  • PRD executive summary / overview
  • Architecture or tech-stack page in the team wiki
  • DevOps / release notes for environment URLs
  • Product owner for objectives and users

4. Step by step

  1. Copy the folder 00_context-template/ to 00_context-<project>/ (do this once per project).
  2. Open 01_context_project.md in the copy and replace each [PLACEHOLDER] using the sources above.
  3. Delete lines that do not apply; keep [Requires clarification] for anything unknown.
  4. Compare with the filled example in 00_context-vwo/ if you are unsure of the level of detail.
  5. Save. The file is now reusable in every Daily QA template.

5. Common mistakes

MistakeDo this instead
Guessing the tech stack from the UIWrite [Requires clarification]; a wrong stack leads to wrong test ideas.
Pasting real credentials next to the URLsNever. Credentials belong in a local .env, not in prompts.

6. Check before you use it

  • No [PLACEHOLDER] left unfilled (filled or marked [Requires clarification]).
  • Every fact can be traced to a source document.
  • No real credentials, tokens or personal data.
