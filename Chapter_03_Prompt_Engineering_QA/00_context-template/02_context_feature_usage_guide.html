Feature Context

Captures the requirements of the one feature you are testing right now, with stable IDs.

Blank file: 02_context_feature.md · Filled example: 00_context-vwo/02_context_feature.md

1. Why this file matters

This is the single source of truth for test case design, RTM and coverage. The IDs (F-01, F-02…) are what the other templates trace back to.

When to fill it

Once per feature or story. Make a copy per feature if you test several in parallel.

Golden rule

Only write what a source document says. Anything else is [Requires clarification].

2. Where to find the information

  • The PRD section for the feature
  • The user story / Jira ticket and its acceptance criteria
  • Output of Daily template 01 Requirement Analysis

3. Fill it in, field by field

SectionWhat to writeExample (VWO pack)
Feature: Name, Goal, SourceWhat the feature lets the user do and where the requirement comes from.Login (email + password) · Authenticate and open the dashboard · PRD 'Login Process'
Requirements tableOne requirement per row, wording copied from the source, a stable ID.F-01 | Email and password login with secure validation | Login Process
Acceptance criteriaThe ticket's AC exactly as written.AC-01: Invalid credentials must not grant access
Not specified in the sourceEverything the source does not say: messages, limits, roles, timeouts.Exact error message text: [Requires clarification]

4. Step by step

  1. Copy the folder 00_context-template/ to 00_context-<project>/ (do this once per project).
  2. Open 02_context_feature.md in the copy and replace each [PLACEHOLDER] using the sources above.
  3. Delete lines that do not apply; keep [Requires clarification] for anything unknown.
  4. Compare with the filled example in 00_context-vwo/ if you are unsure of the level of detail.
  5. Save. The file is now reusable in every Daily QA template.

5. Common mistakes

MistakeDo this instead
Rewording requirements 'to make them clearer'Copy the source wording; put your interpretation in a question instead.
Renumbering IDs between runsKeep IDs stable; RTM and coverage reports depend on them.
Deleting the 'Not specified' sectionKeep it. It is what stops the model inventing limits and messages.

6. Check before you use it

  • No [PLACEHOLDER] left unfilled (filled or marked [Requires clarification]).
  • Every fact can be traced to a source document.
  • No real credentials, tokens or personal data.
